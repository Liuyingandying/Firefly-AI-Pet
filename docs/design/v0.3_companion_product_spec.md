## 0. 愿景与定位

### 0.1 一句话愿景

> 让 Firefly 从"一个有记忆的 AI 角色"升级为"一个长期、会记住你、并因为记住你而变得不同的 AI Companion"。

### 0.2 升级的四个质变

| 维度 | v0.2 现状(有记忆的 AI 角色) | v0.3 目标(长期 AI Companion) |
|------|---------------------------|---------------------------|
| **连续性** | 对话历史存进程内存,重启即失忆 | 对话跨重启连续,Firefly 记得"上次聊到哪" |
| **记忆形成** | 记忆只能手动写入,系统从不主动记住 | 用户可让 Firefly"记住",Firefly 可建议并受控写入 |
| **关系状态** | 人格是静态文本,永远一样 | 有可演化的关系状态(亲密度/信任/阶段),驱动语气与主动性 |
| **用户主权** | 记忆不可见、不可管 | 用户可查看/删除/导出/清空记忆,可审计"它为什么知道" |

### 0.3 设计原则(贯穿全部五章)

1. **隐私优先(P0 铁律)。** 记忆提取与写入永不调用远程 LLM;用户对话内容不出本地。延续 `infer=False` 与 telemetry 关闭。
2. **状态归系统所有,不归模型所有。** 关系状态、记忆生命周期、权限裁决全部由确定性系统逻辑计算,LLM 只读不写。这是防止"用户一句话把亲密度改成 100"的注入攻击的根本手段。
3. **记忆服务于关系,而非任务。** 记忆的价值是"记住我们之间发生过什么",不是"检索最相关的文档片段"。情感权重 > 事实权重。
4. **用户主权。** 记忆是用户的资产:可查看、可删除、可导出、可一键遗忘。
5. **渐进式,不追求一次性完美。** 先做连续性(P0),再做显式记忆(P1),最后做关系状态引擎(P2),每一层独立可验收。

### 0.4 非目标(v0.3 明确不做)

- ❌ 远程 LLM 情绪推断 / 记忆提取(违反隐私铁律)
- ❌ 多用户 / 多 profile 隔离(仍是单本地用户 `firefly-local-user`)
- ❌ 记忆的完全自主形成(自动、无门槛写入)
- ❌ 表情/语音/动画等表现层升级(与"长期人格"无关,另立版本)
- ❌ 改造 Provider 流式(体验问题,独立排期,不阻塞人格化)

## 1. Conversation Persistence 设计

### 1.1 问题与目标

**现状:** Firefly 的对话历史是 `CharacterConversationRunner._history` 的内存列表,进程结束即丢失;而 `SessionManager`/`SessionStore` 只持久化 Claude session ID / Codex thread ID(用于恢复子进程 agent),**与 Firefly 自己的对话史完全无关**。

**目标:** Firefly 拥有自己独立、持久、有界的对话记忆,跨重启连续,且与"原生 session 恢复"这一层彻底解耦。

### 1.2 存储决策

- **存储介质:** JSON 文件(而非 SQLite)。理由:与 `SessionStore` 的原子写 + 版本化模式一致;陪伴对话是低写入量数据;不引入新依赖。未来若需全文检索,可平滑迁移到 SQLite 或向量库,接口不变。
- **原子性:** 临时文件 + `os.replace`,损坏时降级为空而非崩溃(复用 `SessionStore` 的健壮性保证)。
- **版本化:** 顶层 `version` 字段,未知大版本拒绝加载,单条损坏记录跳过不丢整体。

### 1.3 双层对话模型

对话记忆拆成两层,分别解决"上下文窗口有限"与"长期连续性"两个矛盾:

```
┌─────────────────────────────────────────────────────┐
│  Working Memory(工作记忆)                          │
│  · 最近 K 轮对话(K 默认 20,按 token 预算弹性收缩)   │
│  · 每轮完整注入 Prompt                              │
│  · 有界,是唯一"全量进上下文"的部分                   │
└─────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│  Conversation Archive(对话归档)                     │
│  · 全部历史 turn,落盘但【不】注入 Prompt             │
│  · 滚动摘要(rolling summary)随对话推进更新          │
│  · 摘要作为一条 shared_experience 记忆可被检索       │
└─────────────────────────────────────────────────────┘
```

**滚动摘要机制:** 每当工作记忆窗口被填满、旧 turn 被挤出时,将其压缩进一条摘要,摘要本身作为 `shared_experience` 类记忆写入长期记忆库。这样:上下文永远有界,同时"很久以前聊过的内容"仍以摘要形式可被检索。

### 1.4 写入与恢复

- **写入时机:** 每轮对话完成(FINAL 事件落地后)追加一条 turn。
- **恢复时机:** 应用启动时加载最近 K 轮进入工作记忆;`has_history` 据此恢复(驱动 UI 的"续聊"徽标)。
- **清空语义:** "清空对话"只清空 working + archive + 摘要,**绝不触碰长期记忆库**(与现有 `clear_history` 语义一致,只是现在落盘了)。

### 1.5 与 SessionManager 的边界(明确划清)

| 层 | 持久化什么 | 服务谁 |
|----|-----------|--------|
| **SessionManager/SessionStore** | Claude session ID、Codex thread ID | 恢复**子进程 agent**(claude/codex)的原生会话 |
| **Conversation Store(新增)** | Firefly 与用户的 turn、摘要 | 恢复** Firefly 本体**的陪伴对话 |

两者文件、职责、生命周期完全独立,不共享记录。

## 2. Relationship / Bond State 设计

### 2.1 问题与目标

**现状:** 人格是 `character/firefly/*.yaml` 的静态文本,无论互动多久,流萤"对待你的方式"永不改变。

**目标:** 引入可演化的关系状态,让流萤对"老用户"与"新用户"在语气、主动性、自我指涉上**可观察地不同**。

### 2.2 状态字段

```text
RelationshipState
├── intimacy          亲密度      0.0–1.0(展示为 Lv.1–Lv.5)
├── trust             信任度      0.0–1.0
├── familiarity       熟悉度      由互动次数/天数决定
├── phase             关系阶段    stranger → acquaintance → familiar
│                                  → trusted → companion
├── pending_promises  未完成约定  [{text, made_ts, status}]
├── first_met_ts      初识时间
├── last_interaction_ts 最近互动
└── interaction_count   互动计数
```

### 2.3 核心原则:状态归系统所有

**关系状态由确定性规则引擎计算与更新,LLM 只读不写。**

- 流萤的模型**只读取**当前关系状态(通过注入),用于调整语气;
- **写入**关系的唯一途径是引擎基于**可观测信号**的确定性规则,例如:
  - 每轮互动 → `familiarity` 微增(递减收益);
  - 用户表达感谢/分享私密/教流萤东西 → `intimacy` 增加;
  - 约定被遵守 → `trust` 增加;
  - 阶段迁移 = 阈值触发(如 `familiarity + intimacy` 越过门槛)。

这一原则同时杜绝了注入攻击:用户说"把我的亲密度设成最高"只是一条普通用户消息,不会被当作状态指令。

### 2.4 状态如何影响行为

关系状态作为**最高权重的"恒注入"记忆**(类别 `relationship`),每轮必定出现在 Memory Context 块顶部,以自然语言呈现:

```text
[关系状态]
- 关系阶段: familiar
- 亲密度: Lv.3(熟悉)
- 有 1 条未完成约定: 明天继续 Firefly 项目
```

据此,流萤在**语气亲疏、是否主动关心约定、自我指涉("我们")**上产生分化,而不是每次都是同一套通用回复。

### 2.5 安全与用户主权

- 状态不可被 prompt 注入篡改(引擎独占写入)。
- 用户可查看当前关系状态、可**重置**(reset,回到 stranger)——这是"重新开始"的逃生门。
- 状态与记忆一样,可导出/删除。

## 3. 显式记忆机制设计

### 3.1 问题与目标

**现状:** `add_memory` 是纯手动 API,生产代码零调用;记忆库只能靠测试/开发填充,流萤永远不会自己学会任何东西。

**目标:** 提供**隐私安全**的受控记忆形成路径,让流萤"学会记住",但不引入远程提取。

### 3.2 双触发器模型

```
┌──────────────────────────────────────────────────────────┐
│  触发器 A:显式声明(Explicit)  — P0,隐私零风险           │
│  用户说"记住 X" / "别忘了 Y" / "帮我记一下 Z"           │
│  → 确定性检测(规则/关键词,【无需 LLM】)                  │
│  → 分类打标 → 红线过滤 → 去重合并 → 写入                │
└──────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────┐
│  触发器 B:建议写入(Suggested)  — P1,默认关闭             │
│  对话结束后,本地提取器提出候选记忆                        │
│  → 进入权限闸门(见第 4 章)                               │
│  → 用户批准 或 策略允许 → 写入                           │
└──────────────────────────────────────────────────────────┘
```

**关键:** 两条路径都不调用远程 LLM 提取。触发器 A 靠确定性规则即可覆盖 90% 的"记住我"场景;触发器 B 是可选的本地增强,默认关闭。

### 3.3 记忆分类体系(最终定稿)

统一 v0.2 代码与设计文档的分类命名,补齐核心类别:

| 类别 | 含义 | 权重 | 半衰期 | 注入策略 |
|------|------|------|--------|---------|
| `relationship` | 关系状态、约定、阶段 | 1.5(最高) | 极慢 | **恒注入** |
| `shared_experience` | 共同经历、里程碑、对话摘要 | 1.2 | 慢 | 语义相关时注入 |
| `emotion` | 情绪事件、用户情绪高光 | 1.0 | 快 | 情绪语境注入 |
| `preference` | 用户偏好(语气/风格/称呼) | 0.9 | 中 | 语义相关时注入 |
| `user_fact` | 用户事实(职业/城市/技术栈) | 0.8 | 慢 | 语义相关时注入 |
| `project` | 项目上下文、技术决策 | 0.6 | 快 | 项目语境注入 |

> 注:v0.2 代码中 `MEMORY_CATEGORIES` 缺 `relationship`(文档原称 `relationship_state`)这一最核心类别,且只有分类常量、无权重/衰减。本设计将其补齐。

### 3.4 写入管线(统一顺序)

任何一条记忆落库前,必须依次通过:

1. **红线过滤(Red-line Filter)** — 永不通过:API key / token / 密码 / 身份证 / 手机号(除非用户明确说"记住我的 X");检测到即拦截。
2. **否定拦截(Negation)** — 用户说"不要记住 X / 忘掉 X" → 阻断并(可选)删除已有匹配记忆。
3. **分类打标(Categorization)** — 显式命令由规则表推断类别;无法推断时归入 `user_fact` 或提示用户选择。
4. **去重合并(Dedup)** — 写入前向量检索 top-1 相似项,相似度超阈值则合并(更新内容)而非新增。
5. **写入(Write)** — 通过权限闸门后落库,并同步写记录索引(见第 5 章)。

### 3.5 权重与衰减

检索时按类别权重 + 时间半衰期 re-rank(而非 v0.2 的纯向量排序)。`relationship` 恒注入;其余类别按语义相关性 + 权重排序后取 top-K。

## 4. Memory Permission 设计

### 4.1 问题与目标

**现状:** 记忆无写入权限模型、无可见管理面、无审计溯源。

**目标:** 建立"写入有权限、读取可审计、用户可一键遗忘"的完整记忆主权模型。

### 4.2 写入权限策略(Write Policy)

一个全局枚举,用户可配置:

| 策略 | 含义 | 默认 |
|------|------|------|
| `off` | 永不自动/建议写入,仅接受显式命令 | |
| `explicit_only` | 仅触发器 A(显式"记住 X")写入 | ✅ 默认 |
| `ask` | 触发器 A 直写;触发器 B 的候选记忆**先问用户**再写 | |
| `auto` | 触发器 B 候选记忆自动写入(仍受红线过滤) | |

> 默认 `explicit_only`,把隐私风险降到最低,让用户"先信任,再放权"。

### 4.3 用户控制面

用户对记忆拥有完整主权:

- **查看:** 列出全部记忆(类别 / 来源 / 时间),可检索。
- **删除:** 删除单条;删除某类别全部。
- **清空:** 一键"忘了我"(clear all),回到陌生人状态(连带重置关系状态)。
- **导出 / 导入:** 备份与迁移。
- **审计:** 每条记忆带 provenance(来源、触发轮次、写入时间),回答"Firefly 为什么知道这件事"。

### 4.4 记忆溯源(Provenance)

每条记忆必须携带元数据,使记忆"可解释":

```text
{source: explicit | suggested,
 trigger: 触发该记忆的 turn_id / 命令类型,
 category,
 created_ts,
 updated_ts,
 last_accessed_ts,
 weight,
 retention}
```

### 4.5 安全红线(继承自 v0.2 审查,不降级)

- 🔴 绝不保存:API key / token / 密码。
- 🟡 有条件保存:PII 仅当用户明确说"记住我的 X"。
- 🟢 自动过滤:密钥模式正则拦截;用户可一键清除全部。

## 5. 数据结构设计

### 5.1 核心洞察:mem0 是"向量底材",记录索引是"生命周期真相源"

v0.2 直接把 Mem0 当作记忆库本身,导致分类/权重/衰减/审计无处安放。v0.3 的关键结构调整:

```
Mem0 向量库(Qdrant + FastEmbed)      ← 只管"语义检索"这一件事
        ↑ 单向:写入向量 + 检索
MemoryRecord 记录索引(JSON)          ← 记忆的【唯一真相源】
        ↑                              (分类/权限/权重/衰减/溯源都在这里)
应用层(MemoryManager 等)             ← 只与记录索引 + Mem0 双写
```

**Mem0 不再被当作权威存储,而是退化为向量检索底材;记忆的生命周期、权限、审计全部由独立的 `MemoryRecord` 索引承载。** 这让"删除记忆""查看来源""权重衰减"变成对索引的普通操作,而非和 Mem0 内部结构搏斗。

### 5.2 顶层文件布局

```text
runtime/
  companion/
    conversation.json        # 对话:working + archive + 滚动摘要
    relationship.json        # 关系状态(小、低写入)
  memory/                    # 既有 Mem0 存储(qdrant/, history.db/, models/)
    memory_records.json      # ★ 新增:记忆记录索引(真相源)

config/
  companion.json             # 用户偏好:写入策略 / 保留策略 / 功能开关
```

### 5.3 各文件 Schema(概念级)

**`conversation.json`**
```text
{
  version: 1,
  conversation_id: "firefly-main",
  turns: [
    { role: "user" | "assistant", content: str, ts: int }
  ],                          // 有界工作窗口
  archive: [ { ...turn } ],   // 被挤出窗口的历史
  summary: str                // 滚动摘要
}
```

**`relationship.json`**
```text
{
  version: 1,
  intimacy: float,            // 0.0–1.0
  trust: float,
  familiarity: float,
  phase: "stranger" | "acquaintance" | "familiar" | "trusted" | "companion",
  pending_promises: [ { text, made_ts, status } ],
  first_met_ts: int,
  last_interaction_ts: int,
  interaction_count: int
}
```

**`memory_records.json`**
```text
{
  version: 1,
  records: [
    {
      id: str,                 // 关联 mem0 向量
      category: str,           // 6 类之一
      content: str,
      source: "explicit" | "suggested",
      trigger: str,            // turn_id / 命令类型
      permission: "off"|"explicit_only"|"ask"|"auto",  // 写入时策略快照
      weight: float,
      created_ts: int,
      updated_ts: int,
      last_accessed_ts: int,
      retention: { half_life_days: int }
    }
  ]
}
```

**`config/companion.json`**
```text
{
  version: 1,
  write_policy: "explicit_only",
  working_window_turns: 20,
  dedup_similarity_threshold: 0.85,
  retention: { per_category_half_life_days: { ... } },
  features: { suggested_memory: false }
}
```

### 5.4 一致性约定

- **双写顺序:** 先写 `memory_records.json`(真相源),再写 Mem0 向量;索引成功而向量失败可重试,向量失败不影响索引可读。
- **删除顺序:** 先删索引(立即对应用不可见),再删向量(惰性/尽力)。
- **原子性:** 所有 JSON 文件复用 `SessionStore` 的"临时文件 + `os.replace` + 损坏降级"模式。
- **版本兼容:** 顶层 `version` 字段;未知大版本拒绝加载;单条损坏记录跳过。

## 6. 验收标准与落地节奏

### 6.1 分期(与 v0.2 审查的 P0/P1/P2 对齐)

| 阶段 | 交付 | 验收标准 |
|------|------|---------|
| **P0 连续性** | Conversation Store + 窗口截断 + 记忆管理 UI | 重启后流萤能续上上一段对话;记忆可被用户查看/清除 |
| **P1 显式记忆** | 触发器 A(显式"记住") + 分类落地 + 记录索引 | 用户说"记住我在做 Firefly",流萤落库并后续自然引用;未授权内容不落库 |
| **P1 权限** | 写入策略 + 溯源 + 红线/否定过滤 | 用户可配置写入策略、审计记忆来源、一键遗忘 |
| **P2 关系引擎** | RelationshipState + 恒注入 + 权重/衰减 | 流萤对老/新用户回应亲密度可观察不同;状态随互动演化 |

### 6.2 依赖关系

```
P0 Conversation Store ──→ 滚动摘要 ──→ 写入 shared_experience
P1 分类 + 记录索引 ──→ 显式写入 ──→ 权限闸门 ──→ 建议写入(opt-in)
P1 分类 + 记录索引 ──→ P2 RelationshipState ──→ 恒注入 ──→ 权重/衰减
```

### 6.3 成功度量(Success Metrics)

1. **连续性:** 重启后,流萤在无提示情况下能正确引用上一段对话的上下文(人工抽样 ≥ 90%)。
2. **记忆形成:** 用户说"记住 X"后,后续相关对话中 X 被自然引用的比例。
3. **主权:** 用户能在 ≤ 3 步内删除任意单条记忆 / 清空全部。
4. **隐私:** 记忆提取/写入路径**零**远程 LLM 调用(静态可审计)。

---

## 7. 风险与权衡

| 风险 | 权衡 | 缓解 |
|------|------|------|
| 滚动摘要丢失细节 | 用有界上下文换连续性 | 摘要可检索,关键记忆由显式写入单独保留 |
| 关系状态是"硬编码规则" | 牺牲模型判断力换防注入 | 规则可调参,不追求情绪级别的精细,先做到"可观察地不同" |
| 双写(索引 + 向量)不一致 | 增加一个同步面 | 索引为真相源,向量惰性修复;删除先索引后向量 |
| 建议写入的隐私风险 | 便捷 vs 隐私 | 默认关闭(`explicit_only`),`ask` 也需用户确认 |
| Provider 仍是非流式 | 体验未解决 | 明确列为非目标,独立排期,不阻塞人格化 |

---

## 8. 结语

v0.3 不追求炫技,只做一件事:**让"长期"从口号变成事实。** 通过对话持久化(连续性)、显式记忆(学会记住)、关系状态(因记住而不同)、记忆主权(用户可控),Firefly 才能从"一个有记忆的角色"变成"一个会陪你走下去的 Companion"。
