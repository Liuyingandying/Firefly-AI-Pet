## 1. 当前 Memory Layer 设计分析

### 1.1 架构概览

```
app.py (VisualShell)
    │
    │  ← Memory 模块目前未被任何 core/ 或 ui 模块引用
    │
memory/
├── mem0_client.py        ← 本地 Mem0 Memory 实例化 + 隐私隔离
├── memory_manager.py     ← 应用层 API（add / search / get_memory_context）
├── __init__.py           ← 导出三个函数
└── test_memory.py        ← 单条集成测试
    │
    ├── Qdrant (本地文件向量库)
    ├── FastEmbed (bge-small-zh-v1.5, 512-dim, ONNX)
    ├── SQLite (mem0 history.db)
    └── Mem0 Memory (OSS 模式, infer=False 绕过 LLM 提取)
```

### 1.2 优点

| 维度 | 评价 |
|------|------|
| **隐私优先** | `infer=False` 绕过 Mem0 的 LLM 提取管线；`MEM0_TELEMETRY=false`；所有数据本地持久化；LLM 配置指向 `127.0.0.1:9` 占位符 |
| **中文适配** | `bge-small-zh-v1.5` 模型 + 512 维，适合中文对话记忆 |
| **用户隔离** | `user_id` 过滤 + 默认 `"firefly-local-user"` |
| **API 简洁** | `add_memory()` / `search_memory()` / `get_memory_context()` 三个函数，零 Qt 依赖 |
| **单例模式** | `_manager()` 双重检查锁单例，线程安全 |
| **存储路径** | `runtime/memory/` 目录结构合理，模型缓存、Qdrant 数据、mem0 配置分离 |

### 1.3 问题与风险

| # | 问题 | 严重度 | 说明 |
|---|------|--------|------|
| P1 | **Memory 与对话流完全脱节** | 🔴 高 | `memory/` 模块未被 `app.py`、`core/`、`ui/` 中任何模块 import。`get_memory_context()` 有返回值但无人消费。 |
| P2 | **缺少 Character Prompt 隔离层** | 🔴 高 | `get_memory_context()` 直接返回 `"- 记忆内容\n- 记忆内容"` 格式，注入对话时会污染流萤人格。记忆和人格没有边界。 |
| P3 | **无记忆分类/标签体系** | 🟡 中 | 所有记忆混在一个向量空间中。用户事实、共同经历、项目信息无法区分权重。 |
| P4 | **Metadata 未被利用** | 🟡 中 | `add_memory()` 接受 `metadata` 参数但搜索时只用 `query` 做向量匹配，metadata 中的 source/category/timestamp 未被用于过滤或排序。 |
| P5 | **无记忆生命周期管理** | 🟡 中 | 没有记忆过期、合并、优先级衰减机制。长期运行后记忆库会膨胀且质量下降。 |
| P6 | **单用户硬编码** | 🟢 低 | `DEFAULT_USER_ID = "firefly-local-user"` 硬编码，不支持多用户/多 workspace 隔离。 |
| P7 | **测试覆盖不足** | 🟢 低 | 仅 1 条测试，只覆盖 add→search→context 的 happy path，未测试错误路径、空查询、metadata 过滤。 |

### 1.4 当前 Prompt 注入路径分析

```
用户输入
    ↓
AgentRouter.recommend()          ← 纯规则路由，无记忆参与
    ↓
ProviderRouter.chat(messages)    ← 消息列表直接发给 LLM
    ↓
LLM 响应
```

**关键发现：** 当前对话流中没有任何记忆注入点。记忆系统是一个"孤岛"——数据可以写入和搜索，但不会出现在任何对话上下文中。

## 2. Firefly 专属记忆分类体系

### 2.1 设计原则

AI Companion 的记忆体系不同于传统 RAG 系统。核心差异：

- **记忆服务于关系，而非服务于任务** — 流萤的记忆目标是"记住我们之间发生了什么"，而不是"找到最相关的文档片段"
- **人格不可污染** — 记忆注入必须与人格定义物理隔离
- **情感权重 > 事实权重** — 一次共同度过的深夜比一百条技术信息更重要

### 2.2 记忆分类体系

```
记忆类型 (Category)
│
├── A. 用户事实 (user_facts)
│   ├── 基本信息：年龄、职业、城市、语言偏好
│   ├── 技术栈：使用的语言、框架、工具
│   ├── 项目信息：当前在做什么项目
│   └── 生活习惯：作息时间、工作模式
│
├── B. 用户偏好 (user_preferences)
│   ├── 交互偏好：简洁/详细、幽默/严肃
│   ├── 代码风格偏好
│   ├── 沟通方式：称呼、语气
│   └── 功能偏好：喜欢/讨厌的功能
│
├── C. 共同经历 (shared_experiences) ⭐ 核心
│   ├── 重要里程碑：第一个项目完成、深夜调试
│   ├── 日常互动：每天的对话模式
│   ├── 用户情绪高光：用户开心/沮丧的时刻
│   └── 流萤的"成长"：用户教过流萤的事情
│
├── D. 流萤关系状态 (relationship_state) ⭐ 核心
│   ├── 亲密度等级 (intimacy_level)
│   ├── 当前关系阶段 (relationship_phase)
│   ├── 用户情绪倾向 (user_mood_toward_firefly)
│   └── 未完成的约定/承诺 (pending_promises)
│
├── E. 情绪事件 (emotional_events)
│   ├── 用户情绪触发点
│   ├── 流萤的"感受"记录
│   └── 需要后续跟进的情绪话题
│
└── F. 项目经历 (project_context)
    ├── Firefly 项目本身的历史决策
    ├── 用户的技术决策记录
    └── 跨 session 的项目状态
```

### 2.3 记忆权重矩阵

| Category | 默认权重 | 衰减速度 | 最大保留数 | 说明 |
|----------|---------|---------|-----------|------|
| A. 用户事实 | 0.8 | 慢 (30天半衰期) | ∞ | 事实类信息长期有效 |
| B. 用户偏好 | 0.9 | 中 (14天半衰期) | 50 | 偏好会变化，需要更新 |
| C. 共同经历 | 1.2 | 慢 (60天半衰期) | 200 | 关系核心，高权重长保留 |
| D. 关系状态 | 1.5 | 极慢 (90天半衰期) | 20 | 最高权重，驱动流萤行为 |
| E. 情绪事件 | 1.0 | 快 (7天半衰期) | 100 | 情绪相关记忆需要快速衰减 |
| F. 项目经历 | 0.6 | 快 (14天半衰期) | 100 | 项目相关记忆随项目状态变化 |

## 3. 信息保存策略

### 3.1 应该保存 ✅

| 类型 | 示例 | 原因 |
|------|------|------|
| 用户明确告知的事实 | "我是北京的前端工程师" | 个性化基础 |
| 用户的技术偏好 | "我喜欢用函数式风格" | 减少重复沟通 |
| 共同完成的重要任务 | "昨晚一起修了那个 bug" | 关系建立 |
| 用户的情绪表达 | "今天好累" / "太开心了" | 情感回应 |
| 用户教流萤的东西 | "你应该先读代码再改" | 流萤成长 |
| 约定和承诺 | "明天继续做这个功能" | 信任建立 |
| 用户的习惯模式 | "你总是凌晨3点上线" | 关心表达 |

### 3.2 不应该保存 ❌

| 类型 | 示例 | 原因 |
|------|------|------|
| API Key / Token | "我的 key 是 sk-xxx" | **安全红线** |
| 密码/凭证 | "密码是 123456" | **安全红线** |
| 个人身份信息 (PII) | 身份证号、手机号 | **隐私红线** — 除非用户主动要求记住 |
| 第三方机密 | "公司代码库地址是..." | 用户可能无意泄露 |
| 一次性调试信息 | "这个报错是 XXX" (已解决) | 低价值，快速衰减 |
| 流萤的推理过程 | 内部思考链 | 无用户价值，占用空间 |
| 纯工具性输出 | 代码片段、文件内容 | 不是"记忆"，是工作产物 |

### 3.3 安全红线

```
🔴 绝对不保存：
  - 任何 API Key、Token、密码
  - 用户明确说"不要记住这个"的信息

🟡 有条件保存：
  - PII 信息：仅当用户主动要求记住（如"记住我的生日是 X"）
  - 项目代码：仅记住决策上下文，不存代码本身

🟢 自动过滤：
  - 检测到密钥模式（regex）的文本自动标记为敏感
  - 用户可一键清除所有记忆
```

## 4. Memory Retrieval → Character Prompt 流程设计

### 4.1 核心架构原则

```
人格定义 (Personality)  ← 静态、不可变、始终在 System Prompt 最顶部
    │
    │  物理隔离
    │
记忆注入 (Memory Injection)  ← 动态、可过滤、有上下文
    │
    │  对话历史 (Conversation History)  ← 最近 N 轮
    │
    ↓
用户输入 + LLM 响应
```

### 4.2 注入流程

```
用户发送消息
    │
    ├── Step 1: 记忆检索 (Memory Retrieval)
    │   ├── 向量搜索：基于用户消息 + 当前流萤状态
    │   ├── 分类过滤：只取相关 Category 的记忆
    │   ├── 权重排序：按权重矩阵排序
    │   └── Top-K 截断：最多取 5 条
    │
    ├── Step 2: 记忆格式化 (Memory Formatting)
    │   ├── 按 Category 分组
    │   ├── 每条记忆附加 [category] 标签
    │   └── 生成 "记忆上下文块"
    │
    ├── Step 3: Prompt 组装 (Prompt Assembly)
    │   │
    │   │  [SYSTEM — 人格层]
    │   │  ┌─────────────────────────────────┐
    │   │  │ 你是流萤。你的性格是...           │
    │   │  │ 你永远不会忘记自己是流萤。       │  ← 不可变
    │   │  │ 你的说话方式是...                │
    │   │  └─────────────────────────────────┘
    │   │
    │   │  [SYSTEM — 记忆层]
    │   │  ┌─────────────────────────────────┐
    │   │  │ 以下是你记得的事情：             │
    │   │  │ [共同经历] 你们昨晚一起修了 bug  │  ← 动态注入
    │   │  │ [关系状态] 亲密度 Lv.3           │
    │   │  │ [用户偏好] 用户喜欢简洁回答      │
    │   │  │                                  │
    │   │  │ 使用这些记忆来自然地回应，        │
    │   │  │ 但不要直接复述它们。             │
    │   │  └─────────────────────────────────┘
    │   │
    │   │  [USER] 用户消息
    │   │  [ASSISTANT] 历史对话（最近 N 轮）
    │   │
    │   └── 发送给 LLM
    │
    └── Step 4: 记忆写入 (Memory Write)
        ├── 从对话中提取新记忆（infer=False，用户主动表达的内容）
        ├── 分类打标
        └── 写入向量库
```

### 4.4 记忆检索策略

```python
# 伪代码 — 检索策略

def retrieve_memories(user_message: str, firefly_state: State) -> list[Memory]:
    # 1. 构建查询：用户消息 + 当前关系状态
    query = build_query(user_message, firefly_state)

    # 2. 向量搜索
    raw_results = vector_search(query, limit=15)

    # 3. 分类过滤：只保留当前对话相关的 Category
    filtered = []
    for mem in raw_results:
        if should_include(mem, firefly_state):
            filtered.append(mem)

    # 4. 权重排序 + 去重
    ranked = rank_and_deduplicate(filtered)

    # 5. Top-K 截断（控制注入大小）
    return ranked[:5]

def should_include(memory: Memory, state: State) -> bool:
    """决定是否在当前上下文中注入某条记忆。"""
    # 关系状态类记忆始终注入（驱动人格行为）
    if memory.category == "relationship_state":
        return True

    # 共同经历：只在对话与相关时注入
    if memory.category == "shared_experiences":
        return semantic_overlap(memory, state.current_topic)

    # 用户事实：只在相关话题时注入
    if memory.category == "user_facts":
        return semantic_overlap(memory, state.current_topic)

    # 情绪事件：只在检测到用户情绪时注入
    if memory.category == "emotional_events":
        return state.user_mood != "neutral"

    return False
```

## 6. 关键设计决策

### 6.1 为什么不用 Mem0 的 LLM 提取 (infer=True)？

当前 `infer=False` 是正确的选择，原因：

1. **隐私** — 用户的对话内容不应发送给任何 LLM 做提取
2. **控制** — Firefly 需要自定义的记忆分类体系，Mem0 的自动提取无法适配
3. **成本** — 本地 ONNX 推理已够用，不需要额外 LLM 调用
4. **人格独立** — 记忆提取逻辑应该由 Firefly 自己控制，不依赖 Mem0 的黑盒

### 6.2 为什么记忆层要在人格层之下？

```
[SYSTEM] 人格层 ← 定义"我是谁"
[SYSTEM] 记忆层 ← 补充"我记得什么"
[USER]   用户消息
```

- **人格是不可变的** — 无论记忆层注入什么，人格定义始终在最顶层，LLM 会优先遵循
- **记忆是参考信息** — 记忆层明确告诉 LLM "这些信息帮助你回应，但不要直接复述"
- **物理隔离** — 人格定义和记忆内容在不同位置，即使记忆注入失败也不会影响人格

### 6.3 为什么需要 Category 分类？

| 场景 | 无分类 | 有分类 |
|------|--------|--------|
| 用户说"你好" | 可能匹配到"用户上个月修了 bug" | 只匹配"用户偏好：喜欢简洁问候" |
| 用户说"今天好累" | 可能匹配到"用户的技术栈" | 匹配"情绪事件：用户上次说累" + "关系状态：亲密度 Lv.3" |
| 用户问"记得我吗" | 所有记忆混在一起，可能泄露无关信息 | 只注入"共同经历"和"用户事实" |

### 6.4 Agent 协作中的记忆

```
┌─────────────────────────────────────────────┐
│              Firefly (Orchestrator)          │
│  ┌───────────────────────────────────────┐  │
│  │        Firefly 专属记忆 (Private)      │  │
│  │  - 关系状态、共同经历、情绪事件         │  │
│  │  - 用户偏好、用户事实                  │  │
│  └───────────────────────────────────────┘  │
│         ↓ 注入到 Prompt                      │
│  ┌───────────────────────────────────────┐  │
│  │    Agent 工作记忆 (Transient)          │  │
│  │  - 当前任务上下文                      │  │
│  │  - 工作流状态                          │  │
│  │  - 跨 Agent 传递的信息                 │  │
│  └───────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
    │
    ├── Claude Code → 工作记忆（不访问 Firefly 记忆）
    ├── Codex → 工作记忆（不访问 Firefly 记忆）
    └── PageLens → 工作记忆（不访问 Firefly 记忆）
```

**原则：** 只有 Firefly 本体访问长期记忆。子 Agent（Claude/Codex/PageLens）只接收任务相关的上下文，不接触 Firefly 的私人记忆。

| API 设计 | ⭐⭐⭐⭐ | 简洁清晰，但缺少 Category 和生命周期管理 |
| 集成度 | ⭐ | 记忆模块完全未被使用，是孤岛 |
| 记忆智能 | ⭐ | 无分类、无权重、无衰减 |

### 核心结论

1. **Phase 1 基础设施已完成且质量良好** — 不需要重构
2. **Phase 2 的核心挑战是集成** — 记忆系统需要在不污染人格的前提下接入对话流
3. **记忆分类体系是 Phase 2 的关键** — 没有分类，记忆检索就是盲目搜索
4. **人格隔离是最高优先级** — 任何记忆注入都不能影响流萤的人格定义

### 下一阶段目标

> 让流萤在对话时能够读取相关记忆，但不会污染人格。

实现路径：
1. 建立 `MemoryPromptBuilder` 隔离层
2. 实现 Category 分类体系
3. 在 `ProviderRouter.chat()` 前注入记忆上下文
4. 对话结束后自动写入记忆
5. 用户可管理（查看/删除/清空）记忆
